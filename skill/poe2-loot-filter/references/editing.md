# 编辑与交付

1. 在源文件定位物品实际命中的规则和覆盖它的通用块。编辑条件用客户端认可的名称，中文注释可帮助定位。先读实际条件再判断，文件名和注释可能过时。
2. 同一块的多种条件共同约束匹配。精确名称用 BaseType == 或 Class == 时，核对完整值，尤其避免把原本故意用作部分匹配的类别批量改成精确匹配。从上向下按实际命中追踪 Show、Hide、Minimal 和 Continue，有 Import 时检查被引入规则的顺序与依赖。具体例外放在能吞掉它的宽泛块之前。改多物品共享规则里的一个物品时，必要时复制条件并拆块，保留其他物品的原行为。
3. 文子过滤按中文章节组织，检查每档独立的规则和末尾全局兜底。当前样本没有 Continue，第 7 档仍放行部分 82+ 底子。保留未知掉落的兜底提示，除非用户点名修改。音效常用相对路径 文子过滤音效\文件.mp3，部署时该子目录应在游戏过滤器目录内。先确认现有路径，再决定是否迁移。
4. 在变更摘要记录原文件、目标档、匹配条件、可见性、样式和原因。用户指定的长期例外用可移植的 Markdown 或 JSON 记录，与过滤器放在同一项目内。最少记录档位、意图、匹配条件、希望的效果和优先关系，基于规则内容定位，行号只用于导航。参照 [配置示例](profile.example.json)。重复应用已有改动时先匹配当前规则，避免重复插入。
5. 对比原版和候选的检查结果，处理候选引入的错误。逐个追踪变更物品、同组对照物品、等级或堆叠边界和宽泛兜底实际命中。比较规则顺序、能见度、音效路径和依赖。使用目标区服和版本客户端加载候选并检查报错，有条件时核对代表性掉落。若能使用目标区服官方在线验证入口，可将语法校验用于补充，涉及账号写入或发布时按用户授权范围操作。没有可用客户端时明确报告尚未实际加载。
